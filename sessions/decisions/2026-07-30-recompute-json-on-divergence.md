# 로컬과 origin이 갈라지면 데이터 JSON은 병합하지 말고 재계산한다

## Context

수집 워크플로가 하루 2회(04:37 / 12:07 KST) `main`에 직접 푸시한다. 로컬에서 코드를 고치는 동안 스케줄 수집이 끼어들면 `site/data/*.json`과 `state/seen/*.json`이 양쪽에서 갈라진다. 2026-07-30 세션에서 실제로 발생했다 — 작업 중 `525b2e2`(05:50Z)가 origin에 올라왔고 로컬에는 05:39Z 수집분이 커밋돼 있었다.

SPEC 4.4가 워크플로 **내부**의 push 재시도에 대해서는 "병합이 아니라 재계산"을 규정하지만, 사람/에이전트가 로컬 브랜치를 들고 있을 때는 다루지 않는다.

## Decision

origin과 데이터 파일이 갈라졌을 때 `git merge`나 `git rebase`로 JSON을 합치지 않는다. 다음 순서로 처리한다.

1. `state/seen/{source}.json`을 양쪽에서 꺼내 **어느 쪽이 상위집합인지 확인**한다. 로컬 id 중 origin에 없는 것이 0건이면 로컬 데이터 커밋은 버려도 유실이 없다.
2. 로컬 **데이터 커밋을 버린다**. 코드·문서 커밋만 origin 위로 리베이스한다. 두 쪽이 건드리는 파일이 겹치지 않으므로 충돌 없이 붙는다.
3. 머지 후 **컬렉터를 다시 돌려** 데이터를 재생성하고 새 `collect` 커밋으로 남긴다.

1번에서 로컬이 상위집합이거나 양쪽에 서로 없는 id가 있으면 이 절차를 그대로 쓰지 말고 멈춘다.

## Rejected alternatives

- **`git merge` / `git rebase`로 JSON 합치기** — 샤드는 1행 1항목 append-only라 얼핏 라인 머지가 될 것처럼 보이지만, `manifest.json`은 pretty-print된 중첩 객체라 라인 머지가 구조를 깬다. `seen` 인덱스는 정렬된 배열이라 양쪽 삽입이 겹치면 조용히 어긋난다. 깨진 seen 인덱스는 아카이브 전체 중복이라는 최악의 결과를 만든다(SPEC 3).
- **`git checkout --ours/--theirs`로 파일 단위 선택** — 파일별로 고르면 `manifest.months[].counts`와 실제 샤드 내용이 어긋난다. manifest는 샤드에서 파생된 값이라 따로 고를 수 있는 것이 아니다.
- **로컬 데이터 커밋을 살리고 origin 것을 되돌리기** — origin 데이터는 이미 배포됐고 다른 기기에서 볼 수 있다. 되돌리면 그 사이 수집분이 사라진다.

## Consequences

- 로컬에서 컬렉터를 돌린 결과는 **언제든 버려질 수 있는 것**으로 취급한다. 로컬 수집은 검증 수단이지 보존 대상이 아니다. seen 인덱스가 정본이므로 재실행이 항상 같은 상태로 수렴한다.
- 코드 커밋과 데이터 커밋을 **처음부터 분리**해야 이 절차가 성립한다. 한 커밋에 코드와 `site/data/`를 섞으면 데이터만 버릴 수 없다. 저장소의 기존 `collect <timestamp>` 커밋 관례를 유지할 것.
- 재계산 후 커밋 전에 `node src/verify.ts`를 돌린다.
